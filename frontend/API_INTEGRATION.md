# フロントエンドのAPI連携

OpenAPIと `src/api/generated/` の生成型・生成クライアントを使用する。
生成コードとOpenAPI定義はこの変更では編集していない。通信は既存の
`authenticatedRequest` を通し、認証ヘッダーとトークン更新を共有する。

## 型と取得処理の整理

| 対象         | 使用する生成型・実装                                                                                                                                                                                  |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 企業一覧     | `CompanyListItem`、`CompanyPriority`。追加、志望度変更、並べ替え、選考結果変更をAPIへ保存する。選考IDは企業詳細から取得する。                                                                         |
| 選考         | `Selection`、`SelectionStepResponse`、`SelectionStatus`。旧ステータスへの相互変換を削除。APIに存在しない開催日時・ステップ番号・isActiveを旧modelから引き継がない。                                   |
| タスク       | `Task`、`CreateTaskRequest`、`UpdateTaskRequest`。一覧／企業詳細／ホームで同じ処理を使用。追加、編集、完了変更、削除、一括削除に対応。                                                                |
| イベント     | `Event`、`EventCategory`、`CreateEventRequest`。カレンダーと企業詳細の追加、編集、削除に対応。終日は日付、時間指定はタイムゾーン付き日時を送信し、不使用項目はnullにする。                            |
| ES           | `Essay`、`EssayGroupListItem`、各リクエスト型。グループごとの取得結果をそのまま保持。グループIDのnullはURLパラメーターの`unclassified`に対応させる。作成、編集、削除、グループの並べ替えをAPIへ保存。 |
| ドキュメント | 一覧は`DocumentListItem`、本文は`Document`として別々に保持。本文検索を維持するため、一覧取得後に各詳細を取得する。追加、本文保存、削除、並べ替えに対応。                                              |

タスク・イベント・ES・ドキュメント・企業の不要な初期モックと旧modelを削除した。
フォームの分割日時入力、ドラッグ中の表示順、送信者メニュー、ローディング／エラー等はUI状態として保持する。

- データプロバイダーは認証済み領域でマウントし、ログイン前の取得とログアウト後のデータ保持を避ける。
- 月変更・画面離脱時は古い読込要求を中断する。
- 保存／削除ダイアログは完了を待ち、失敗時は閉じずにエラーを表示する。
- 企業とドキュメントのドラッグは終了時に保存する。キャンセル時は表示順を戻す。
- 再取得に失敗しても成功済みの作成要求を失敗扱いにせず、取得エラーとして表示する。
- ドキュメント本文は「保存する」で明示的に保存する。

## 仕様による表示範囲

イベント一覧APIは月単位。カレンダーは6週間のグリッドにかかる月を取得し、
直近の予定欄もその取得範囲を対象とする。ホームの予定件数と一覧は今月分に限定し、
ラベルにも明示した。期間無制限の未来予定一覧・総件数を一度に取得するAPIはない。

## 検証

API疎通確認は行わない。`frontend/`で以下を実行する。

```sh
npx tsc -b
npm run build
npm run lint
```

生成型のLint警告や、既存のフォント参照・バンドルサイズに関するビルド警告は
生成コードやデザインを変更して解消する対象には含めていない。

## 認証と保護されたURLへのアクセス

保護されたURLへの直接アクセス・画面遷移時は、画面のデータ取得を始める前に
生成クライアントの `getCurrentUser` でトークンを確認する。リロード直後など
アクセストークンがない場合は、先にHttpOnly Cookieで復元してから確認する。
既存のアクセストークンの確認が401の場合は
HttpOnly Cookieで一度だけトークンを更新し、再度 `getCurrentUser` を確認する。
認証できなければ `/login?reason=login-required&returnTo=...` へ遷移し、
ログインが必要な旨を表示する。ログイン成功後は元のURLへ戻る。
通信障害やサーバーエラーの場合はログイン要求に置き換えず、再試行を表示する。

通常APIの401だけでセッションを破棄せず、`getCurrentUser` で確認する。
同時確認は共有し、過去のログインに属する遅延レスポンスは現在の状態を上書きしない。
別ユーザーのログイン後に以前のリクエストを再送しない。

バックエンドはERRORディスパッチの再認証を行わず、元の404/500等を維持する。
Viteではタスク・イベント・ドキュメント・ESもバックエンドへ転送し、画面URLへの
HTMLリクエストはSPAとして処理する。

認証のフロントエンド回帰テストは `npm run test:auth` で実行する。
実API・DBへの接続は不要。

## Docker Composeでバックエンドの修正を反映する

バックエンドはソースのボリュームマウントではなく、DockerfileでビルドしたJARを
実行する。ソース変更後の `docker compose restart backend` だけでは更新されない。
プロジェクトルートで以下を実行してイメージを再ビルドし、コンテナを作り直す。

```sh
docker compose up -d --build --no-deps backend
```

今回調査した稼働中の旧JARにはAuthControllerしか含まれず、企業などのAPIは
未収録だった。また旧SecurityConfigはERRORディスパッチも認証対象としており、
存在しないAPIの404が401に置き換わる状態だった。現在のソースでは各APIを実装済みで、
ERRORディスパッチは元のステータスを維持する。

認証拒否時はバックエンドのログに対象のメソッド・パス・ディスパッチ種別、
Authorizationヘッダーの有無を出力する。JWT検証失敗時は例外の種類も記録する。
トークン本体や例外メッセージは記録しない。
